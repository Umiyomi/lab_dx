# ラボDX：研究資産管理基盤の構築

## 1. 目的

ラボDXで扱う課題は次の二つである。関連するが、管理対象・目的・運用強度が異なるため、段階的に導入する。

| 領域 | 問い | 目的 |
|------|------|------|
| 研究資産管理 | 何がどこにあり、誰が管理しているか | 失わず、再利用・継承可能にする |
| 研究状態管理 | 研究がどこまで進み、どこで停滞しているか | 完了可能な状態を維持する |

---

## 2. 現状の課題

### 研究資産

| 課題 | 内容 |
|------|------|
| 所在の個人依存 | 保管場所が個人PC・個人フォルダに閉じている |
| 手順の暗黙知化 | 解析手順がドキュメント化されていない |
| 再利用困難 | スクリプト・集計処理の再利用が困難 |
| 対応関係の不明確 | ドキュメントと成果物の対応が追えない |
| 散逸リスク | 卒業・異動時に資産が失われる |

**管理対象の母集団が未定義のため、管理状態を判断できない。**
ファイルAの存在が知られていなければ、ファイルAを第三者が管理することはできない。

### 研究状態

| 課題 | 内容 |
|------|------|
| 進捗の不透明 | 各研究の到達点がラボとして把握できない |
| マイルストーン未分解 | 「進行中」のまま成果物単位の分解がない |
| 停滞の見逃し | 長期間停止している研究・ボトルネックを検出できない |

---

## 3. 資産管理と状態管理の違い

| | 研究資産管理 | 研究状態管理 |
|--|--------------|--------------|
| 問い | 何があるか | 何をしているか |
| 対象 | データ・コード・文書 | タスク・成果物・進捗 |
| 目的 | 機密・再利用・継承 | 完了・論文化 |
| 主な利用者 | 研究者・マネージャ | 研究者・PI・マネージャー |
| 技術基盤 | NAS / Git / 台帳 | Issue / Milestone / Project |
| 導入上の負荷 | データ構造化 | Issue管理 |

---

## 4. 研究資産管理

### 4.1 対象と目的

**対象:** 生データ、加工データ、スクリプト、解析環境、ドキュメント、図表、論文原稿、研究ノウハウ（文書化済みのもの）

**目的:** 存在・所在・責任者・機密性・更新状態を把握し、再利用・継承可能な状態にする。

### 4.2 成熟度（段階導入）

#### Level 1：所在管理

ラボとして資産の存在と所在を把握する。

管理項目: 研究名、担当者、利用データ、保存場所、機密性、管理責任者

```text
Research A
  Data:     NAS:/survey/2026/raw/
  Code:     GitHub:/lab/researchA
  Document: NAS:/report/
```

#### Level 2：構造化管理

個人ごとの管理方法からラボ標準へ移行する。

管理項目: ディレクトリ構造、ファイル命名規則、README、メタデータ

```text
research_A/
├── data
├── metadata
├── analysis
├── results
└── docs
```

#### Level 3：再現可能管理

第三者が再利用できる状態にする。

導入要素: Git、バージョン管理、解析履歴、実行環境、dependency管理

### 4.3 台帳設計

Excel一覧ではなく、正規化した3エンティティで管理する。

```text
Research
 ├── research_id
 ├── title
 ├── owner
 └── status

Asset
 ├── asset_id
 ├── type
 ├── name
 ├── location
 ├── owner
 └── version
```

**Relation（利用関係）** で研究と資産の多対多を表現する。同一データが複数研究で利用されるケースに対応する。

```text
Research R001 → GPS data, Analysis code, Manuscript
Research R002 → GPS data
```

### 4.4 データ形式（JSON）

階層・関係性の表現とスキーマ検証のため、JSONで台帳を管理する。

```json
{
  "research_id": "R001",
  "title": "研究テーマ",
  "owner": "student_A",
  "assets": [
    {
      "type": "dataset",
      "name": "raw_data",
      "location": "NAS/path",
      "confidential": true
    },
    {
      "type": "code",
      "name": "analysis_script",
      "location": "GitHub/repository"
    }
  ]
}
```

JSON Schemaで必須項目・所在・管理者・バージョンを検証する。

### 4.5 保存基盤

| 基盤 | 対象 | 役割 |
|------|------|------|
| GitHub | スクリプト、ドキュメント、Issue、変更履歴 | コードと研究プロセスの履歴管理 |
| NAS + Git | 大容量・非公開データ、原データ、中間生成物 | データ資産の保存 |

保存場所の選択より、研究との紐付け（台帳上の追跡）を優先する。

GitHubは個人アカウント配下ではなく、**ラボの Organization** 下にリポジトリ・Issue・Projectsを置く。個人アカウントはメンバー参加用とし、資産の所有者はラボに固定する。NASアカウントもラボ所有とする。

| 対象 | 所有者 |
|------|--------|
| GitHub Organization | ラボ |
| Repository | ラボ |
| Issue / Projects | ラボ |
| GitHub Account | 個人 |
| NASアカウント | ラボ |

Organizationの運用目的は、資産の所有者をラボに固定したうえで、役割に応じた読み書き権限を分離することである。

| 状況 | 読み取り | 書き込み | 備考 |
|------|----------|----------|------|
| ラボメンバー | ○ | ○ | 通常の学生・教員 |
| 卒業生 | ○ / × を選択 | 通常は × | 必要に応じて残せる |
| 共同研究者 | ○ | ○ / × | プロジェクトごとに設定 |
| 一般公開 | Publicなら ○ | × | オープンソース等 |

権限は Organization の Team で付与する。

| Team | Repository権限 |
|------|----------------|
| Faculty | Admin |
| Manager | Maintain |
| Students | Write |
| Alumni | なし（Organizationから削除） |

卒業時は Alumni として残すのではなく、原則 Organization から削除する。削除後も個人アカウントの contribution graph は残る。

### 4.6 標準ディレクトリ構造

```text
Research Project
├── raw_data
├── metadata
│   ├── survey_sheet
│   ├── variable_definition
│   └── codebook
├── processed_data
├── analysis
├── results
└── manuscript
```

## 5. 研究状態管理

### 5.1 対象と目的

**対象:** 研究タスク、マイルストーン、成果物、ボトルネック

**目的:** 研究プロジェクトを完了可能な状態に維持する。

### 5.2 成熟度（段階導入）

#### Level 1：研究単位の状態把握

ラボ全体の研究状況を俯瞰する。

| 研究 | 状態 |
|------|------|
| 研究A | データ整理中 |
| 研究B | 解析中 |
| 研究C | 論文執筆中 |

PI・マネージャーが「どの研究がどこまで進んでいるか」を把握できる状態にする。

#### Level 2：マイルストーン管理

研究を成果物単位に分解する。

```text
研究A
□ データ整理
□ 解析
□ 結果整理
□ 論文作成
```

#### Level 3：Issueベース管理

研究プロセスを追跡可能な単位に分解する。

```text
Research Question → Milestone → Issue → Deliverable
```

管理対象: Issue状態、担当者、更新履歴、停滞期間、成果物

これにより、長期停止の検出・ボトルネック把握・進捗可視化を行う。

---

## 6. 導入ロードマップ

| Phase | 内容 | 実施事項 |
|-------|------|----------|
| 1 | 研究資産の可視化 | 資産台帳作成、所在管理、管理責任者設定 |
| 2 | 研究資産の標準化 | ディレクトリ標準、README、メタデータ、保存ルール |
| 3 | 研究状態の可視化 | マイルストーン管理、成果物管理、定期レビュー |
| 4 | 研究プロジェクト管理の高度化 | Issue管理、GitHub Projects等、自動レポート、停滞検知 |

資産管理（Phase 1–2）を先に進め、状態管理（Phase 3–4）は可視化の基盤が整ってから導入する。

---

## 7. 研究資産マネージャーの役割

研究内容（仮説・解析手法・科学的判断）は管理しない。可視化と継承可能性の維持が主務である。

### 管理対象

- 資産の存在・所在・責任者
- 資産の継承可能性（台帳・構造・検証）
- 研究プロジェクトの可視化
- 停滞状態の検出可否

### 業務

| 業務 | 内容 |
|------|------|
| 台帳の維持 | 新規研究・資産の登録、所在・管理者の確認、状態更新 |
| 資産状態の検証 | データ／Gitの実在、README、管理者定義をスクリプトで確認 |
| 定期棚卸し | 登録漏れ、所在の明確さ、引継ぎ・再利用可否 |
| 状態の可視化支援 | マイルストーン／Issue運用の整備（Phase 3以降） |

---

## 8. 適用優先領域

紙ベース・アンケート調査系研究を優先導入する。対象資産の関係が不明確になりやすいため。

- 調査票 / 回答データ / コード表
- 集計処理 / 図表 / 報告書

導入時の教育重点はプログラミング技能ではなく、研究データの構造把握とする。

---

## 9. 期待効果

| 項目 | 内容 |
|------|------|
| 機密性 | 所在・権限・秘密度の可視化 |
| 再現性 | データ・スクリプト・条件の対応関係の明示 |
| 引継ぎ | 卒業・異動時の資産散逸防止 |
| 再利用 | 既存資産の横断利用 |
| 進捗把握 | 研究単位・マイルストーン単位での到達点の可視化 |
| 停滞検知 | 長期停止・ボトルネックの早期発見 |

---

## 10. 成功条件

**資産管理（Phase 1–2）**

- 進行中の研究が台帳に登録されている
- 各資産の所在・責任者が特定できる
- 検証スクリプトで実在・必須項目を機械的に確認できる
- アンケート研究で標準ディレクトリ構造が運用されている

**状態管理（Phase 3–4）**

- 進行中の研究に状態（到達段階）が付与されている
- 主要研究にマイルストーンが定義されている
- 長期未更新の研究を検出できる
